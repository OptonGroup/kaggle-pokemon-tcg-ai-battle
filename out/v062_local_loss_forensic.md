## Вопрос 1: почему Munkidori получает энергию только в ~65% игр vs Crustle

**Вердикт: НЕ баг очерёдности гвардов. Две отдельные, обе чинибельные причины: (a) поисковые
эффекты (Poke Pad/Dawn/Petrel/generic take) систематически недооценивают Munkidori относительно
линии атакера, из-за чего он физически появляется на столе медианно на ходу 5 вместо
ожидаемых 1-2; (b) Punk Up (триггер эволюции в Grimmsnarl ex) вытягивает медианно 60% всей
{D}-энергии колоды НАПРЯМУЮ из колоды в руки Marnie-линии, минуя Munkidori по тексту карты —
и это усугубляется тем, что скорер одинаково поощряет КАЖДУЮ эволюцию Grimmsnarl (даже 3-ю/4-ю
избыточную скамеечную копию), у которой Punk Up перетриггерится и добьёт остаток пула.**

Числа (N=30 vs v009a, `traces/`):
- Munkidori бенчится хоть раз в 29/30 (96.7%) игр — деки достаточно (4/60 копий), рисовка не
  проблема.
- `guard=munkidori_energy` срабатывает хотя бы раз в 20/30 (66.7%) — совпадает с независимо
  измеренным `munkidori_energy_guard_pct_games_ge1=0.65` в уже существовавшем
  `results/gates/v062_fidelity_gate.json` (N=40) — две независимые реализации харнесса дают
  один и тот же процент, гвард-логика воспроизводима.
- Проверил гипотезу «перехват другим гвардом раньше по цепочке» напрямую: `guard=energy_attach`
  (шаг 5, энергия для Grimmsnarl ex) стреляет в среднем **0.00/игру vs Crustle, 0.07/игру vs
  Archaludon** — то есть Grimmsnarl практически НИКОГДА не получает энергию через этот гвард
  (он получает её пакетно через Punk Up), и конкуренции за «единственный аттач хода» между
  двумя гвардами на практике почти нет. Гипотеза из задания не подтвердилась.

Механизм (a) — поисковый приоритет, подтверждён построчно в трассе `v009a_crustle_001.json`
(проигрыш, my_pz=6/opp_pz=0, Munkidori впервые на столе только на ходу 15!!!): на ходах 1 и 3
Poke Pad дважды забирает **избыточную** копию Impidimp (`'Poke Pad: Impidimp (line incomplete)'
s=20000`), хотя Impidimp уже в игре, вместо единственно недостающего Munkidori. Причина —
`scoring_grimmsnarl.py::score_to_hand`, ветка `POKE_PAD`:
```python
if cid == IMPIDIMP:
    if poke_pad_line_incomplete(obs):   # True пока Munkidori не в игре -- НЕ про Impidimp!
        return 20000, "..."
if cid == MORGREM:
    return 18000, "..."                 # флэт, без проверки "уже есть?"
if cid == MUNKIDORI:
    return 16000, "..."                 # флэт, ВСЕГДА ниже двух предыдущих
```
`poke_pad_line_incomplete()` корректно вычисляет «тройка не собрана», но бонус применяется
только к ветке Impidimp, а не к реально недостающей карте. Та же иерархия
(Grimmsnarl>Morgrem>Impidimp>Munkidori, без проверки «уже в игре») повторена в `Dawn`,
`Petrel`-generic и generic-fallback ветках того же файла (строки ~1027-1051) — то есть
Munkidori систематически последний в очереди на тутор **в каждом** поисковом эффекте
колоды. Замер по всему корпусу трасс (100 игр): `Poke Pad: Morgrem` выбран 95 раз против
`Poke Pad: Munkidori` 52 раза, хотя обе карты представлены в колоде поровну (4 копии). Медиана
хода первого бенча Munkidori по 60 играм — **ход 5** (среднее 6.4, максимум 23); в 18/60 (30%)
игр Munkidori впервые появляется на ходу 9+ (см. полный список в отчёте прогонов), в 2/60 — не
появляется вовсе за всю игру.

Механизм (b) — структурная растрата {D}-энергии Punk Up, подтверждён по всем 100 трассам
(поиск `ctx22` — шаг раздачи энергии Punk Up): в среднем **6.18 из 10** копий {D}-Energy колоды
уходят через Punk Up за игру (медиана 6, максимум — все 10), причём в 24/97 (25%) игр Punk Up
в одиночку выедает 8-10 из 10 копий. Punk Up по тексту карты цепляет только «Marnie's Pokemon»
(Impidimp/Morgrem/Grimmsnarl) — Munkidori структурно не может получить энергию этим путём и
остаётся зависим от медленного 1-в-ход аттача из руки, для которого в колоде физически может не
остаться карт. Подтверждено прямым сканом руки в `run_combined.py`/`run_games_munk_track.py`:
в играх, где Munkidori бенчится РАНО (ход 1-3) и остаётся живым десятки ходов, но так и не
энергизуется (`traces2/v009a_crustle_005.json`: бенч ход 7, жив минимум до хода 23, `hand_d`
(количество {D} в руке на момент решения) равно 0 при КАЖДОМ скане — просто нет карт энергии в
руке, потому что они уже все вышли через Punk Up на другие цели), гвард не может сработать
не потому что он сломан, а потому что нет качественной опции для него.

Фикс (конкретно, файл `scoring_grimmsnarl.py`):
1. В `score_to_hand`, ветки `POKE_PAD`/`DAWN`/`PETREL`(generic)/generic-fallback: заменить
   общий "line incomplete"-флаг для Impidimp и флэт-приоритеты Morgrem/Munkidori на
   индивидуальную проверку `not has_in_play(obs, MUNKIDORI)` для ветки Munkidori (по аналогии с
   тем, что уже сделано для Impidimp) — дать Munkidori приоритет ≥ Morgrem/Impidimp, когда он
   сам ещё не в игре, а не наоборот.
2. (ниже уверенность, отдельный эксперимент) `score_evolve`: рассмотреть небольшое снижение
   приоритета повторной эволюции в Grimmsnarl ex, когда на столе уже есть живой энергизированный
   Grimmsnarl ex — чтобы не растрачивать остаток пула {D} на 3-ю/4-ю избыточную копию раньше,
   чем Munkidori получит свою энергию. Это может задеть другие метрики (скорость восстановления
   после размена атакера), поэтому чинить отдельно и гейтить.

## Вопрос 2: почему объём Adrena-Brain втрое ниже эксперта (наш ~3.3-3.9/игру vs эксперт 10.68W/6.86L)

**Вердикт: прямое следствие вопроса 1, плюс сильная асимметрия победы/проигрыша внутри наших
собственных игр. Не «структурная слабость», а тот же дефект тутора.**

Правильный подсчёт (правил регэксп в `analyze.py`: изначально считал только opportunistic-ветку
по `_dbg`; полный счётчик — все три ветки `guard=adrena_trigger`):
- vs Crustle (N=30): среднее 3.93/игру, но **9.44 в победах против 1.57 в проигрышах** —
  6-кратный разрыв. Экспертный разрыв 10.68W/6.86L куда мягче (1.5x) — то есть у эксперта
  Adrena работает даже в проигранных играх, у нас в проигрышах он почти не работает вовсе.
- vs Archaludon (N=30): 3.50/игру в среднем, 8.25W / 2.77L.
- Прямая причинно-следственная цепь подтверждена построчно: способность требует
  `max_counters>0` (есть накопленный урон на своих) **и** чтобы движок вообще предложил опцию
  OPT_ABILITY для Munkidori — а это возможно только если у Munkidori есть хотя бы 1 {D}. В 10/30
  проигрышей vs Crustle `guard=munkidori_energy` не сработал НИ РАЗУ за игру → adrena_total=0 в
  9 из этих 10 (единственное исключение — g20, где гвард сработал 1 раз поздно, а adrena всё
  равно 0, видимо из-за нехватки урона/времени). Корреляция «munk_guard=0 → adrena_total=0»
  почти идеальна в убыточных играх.
- Остаток разрыва (3 игры vs Crustle, где `munk_guard` срабатывал 2-3 раза, но adrena всё равно
  0: g24/g26 и т.п.) объясняется тем же паттерном вопроса 1 (b) — гвард срабатывает один раз
  поздно, Munkidori либо гибнет вскоре после (форсированное продвижение в актив под убойный
  удар — Munkidori имеет наинизший приоритет продвижения, `_promo_priority` тир 0, но
  выставляется активным именно тогда, когда на скамейке уже никого лучше не осталось, то есть
  доска уже разгромлена), либо игра просто заканчивается раньше, чем накапливается урон для
  снайпа.

Никакого отдельного бага в «источник counters пуст (Froslass не выходит)» не нашёл: Freezing
Shroud — не единственный источник урона для max_counters, обычный боевой урон от атак
противника тоже считается (`_damage_on = maxHp - hp` по любому из наших покемонов), и в
проигрышных играх урон, очевидно, есть (нас же убивают). Дефицит именно в наличии энергии на
Munkidori, не в наличии урона для снайпа.

Фикс: тот же, что в вопросе 1 (Poke Pad/Dawn/Petrel приоритет Munkidori). Отдельного нового
фикса для Adrena-объёма не требуется — почини причину, вырастет и следствие.

## Вопрос 3: vs v044_archaludon (WR ≈0.13-0.23 по разным N, эксперт 61%)

**Вердикт: смешанная картина — механики вопроса 1/2 (Munkidori-тутор, Adrena bench-routing)
работают КАК СПРОЕКТИРОВАНО и не являются причиной здесь; основной дефицит — структурная гонка
урона/HP, где темп Archaludon (Metal Defender до 220-270 dmg за удар по реконструкции эксперта)
превышает наш темп восстановления после размена атакера. Это ближе к слабости матчапа, чем к
дефекту пилота, но с одним конкретным наблюдением ниже.**

Прочитал 2 экспертные реконструкции (`data/il_grimmsnarl_v2/archaludon_recon/`): даже
ПОБЕДНАЯ экспертная партия — это 17 ходов плотного размена, несколько раз Grimmsnarl ex гибнет и
пересобирается заново (эволюция 2-й/3-й копии), Adrena-Brain и Freezing Shroud работают каждый
ход с обеих сторон.

Проверено по 30 играм + построчному разбору `traces/v044_archaludon_012.json` (проигрыш,
my_pz=5/opp_pz=0):
- **2-я/3-я копия Grimmsnarl выходит**: да, `n_grimm_evolve` среднее 2.27/игру (диапазон 0-4
  по играм) — деку многократно пересобирает.
- **Adrena идёт в скамеечные Duraludon**: да, подтверждено дословно в трассе — `adrena target
  (value): bench i=1 hp=130 moved_hp=30 killable=False n_candidates=1` (ход 4),
  `n_candidates=4` (ход 8) — таргетинг работает и масштабируется по мере роста скамейки
  оппонента, как и задумано в майнинге v062.
- **Shadow Bullet стреляет каждый ход, пока Grimmsnarl жив и активен**: да — в разобранной
  трассе атака подряд на ходах 6 и 8 без пропусков (`n_shadow_bullet` среднее 2.93/игру по
  корпусу).
- Реальная проблема, которая видна в трассе: на ходу 9 форсированное продвижение
  (`guard=promotion`) ставит в актив Munkidori (наинизший приоритет тира) — то есть к этому
  моменту весь более ценный запас скамейки уже израсходован/убит, а Archaludon продолжает бить.
  Игра заканчивается с opp_pz=0 (МЫ НИ РАЗУ не сняли приз) при my_pz=5 — то есть темп боя
  однозначно в пользу оппонента, а не отдельная ошибка пилота в конкретный момент.
- Модуль сознательно ПРОПУСТИЛ «защитный ретрит Grimmsnarl под угрозой большого урона»
  (см. докстринг main.py, пункт 3.5 "SKIPPED") из-за отсутствия информации о руке оппонента —
  это осознанный компромисс, не баг, но именно такой guard мог бы сгладить размен-гонку здесь
  (не проверял отдельно, эффект неизвестен — это скорее гипотеза для отдельного эксперимента,
  не готовый фикс).

Итог: v044-матчап не показал того же класса дефектов, что vs Crustle. Разрыв WR (23% vs
экспертных 61%) вероятнее всего объясняется 1) остаточным эффектом вопроса 1/2 (Munkidori
позже/реже энергизуется → меньше суммарного темпа урона в среднем по корпусу, даже если
конкретно разобранная партия это не показала явно) и 2) отсутствием защитного
ретрита/протекции инвестиций в Grimmsnarl — оба тянут в одну сторону («наш темп размена
медленнее эксперта»), но я не нашёл однозначного логического бага уровня вопроса 1.

## Вопрос 4: расхождение 14.0% (N=300, gate_v062_regression.py) vs 2.5% (N=40, gate_behavioral_fidelity.py) на v009a

**Вердикт: преимущественно шум выборки при низком базовом рейтине побед, НЕ системный баг
харнесса. Подтверждено тремя независимыми повторными замерами.**

Прочитал оба скрипта построчно. Механические отличия нашёл, но ни одно не объясняет разрыв:
- `MAX_MOVES_PER_GAME=2000` (regression) vs `DEFAULT_MAX_MOVES=600` (fidelity, реально
  использован в прогоне, который дал 2.5%) — проверил сохранённые в
  `results/gates/v062_fidelity_gate.json` реальные длины 40 игр vs Crustle: min 105 / медиана
  137 / max 217 ходов — ни одна игра близко не подошла к лимиту 600. Усечения не было.
- Формула `win_rate`: regression считает `(wins+0.5*draws)/n_total` (тайм-ауты/иллиган попадают
  в знаменатель), fidelity считает `win_ct/(win+loss+draw)` (аномалии исключены из
  знаменателя, ничья = 0, не 0.5). В конкретном прогоне (38L/1W/1D, 0 аномалий) разница даёт
  максимум ~1.25пп — не объясняет 11.5пп разрыва.
- Порядок сторон (`our_first = gi%2==0`), детект победителя (`result != -1` / `result>=0`),
  загрузка колод — идентичны по существу.

Прямая проверка гипотезы «шум»: перегонял ту же пару (мой снапшот vs `v009a_crustle`) ТРЕМЯ
независимыми харнессами (все на N=20-30, разные seed-схемы — напоминаю, встроенный RNG движка
не управляется python-стороны, см. собственный докстринг `gate_behavioral_fidelity.py` про это
известное ограничение):
| прогон | N | WR |
|---|---|---|
| `run_games.py` | 30 | 30.0% (9W) |
| `run_games_munk_track.py` | 25 | 12.0% (3W) |
| `run_combined.py` | 20 | 0.0% (0W) |
| **пул трёх** | **75** | **16.0% (12W)** |
| официальный `gate_v062_regression.py` | 300 | 14.0% (42W) |
| официальный `gate_behavioral_fidelity.py` | 40 | 2.5% (1W) |

Три моих независимых прогона дают разброс от 0% до 30% на N=20-30 — даже больший размах, чем
разница между двумя официальными гейтами. Пул всех трёх моих прогонов (16.0%, N=75) ложится
близко к официальному N=300 (14.0%), подтверждая его как более надёжную оценку. Формально:
при истинном p=0.14 и N=40, P(X≤1)≈1.8% — редкое, но не невозможное событие; с учётом того, что
в фингер-принт прогоне тестировалось 5 разных оппонентов одновременно (multiple comparisons),
шанс, что ХОТЯ БЫ один из пяти так провалится по чистой случайности, заметно выше (~9%).
v009a/Crustle — структурно высокодисперсный матчап для этой колоды (Rock Inn отрезает основной
источник урона Shadow Bullet, so исход сильно зависит от того, успевает ли Adrena-Brain
раскрутиться до того, как оппонент выстроит атаку — а это именно то, что зависит от неуправляемой
рисовки, см. вопрос 1/2) — что и объясняет, почему именно этот матчап дал самый большой разброс
между гейтами, а vs Alakazam/mirror оба гейта сошлись почти точно (0.95 vs 0.9166-0.95, 0.50 vs
0.48).

Рекомендация: доверять N=300 regression-гейту как основной оценке WR по этому матчапу;
N=40 fidelity-гейт использовать для его собственной цели (проверка поведенческих метрик типа
`munkidori_energy_guard_pct_games_ge1`, которая, кстати, СОШЛАСЬ с моим независимым замером на
65-67% — то есть сам по себе гейт корректен, просто N=40 недостаточно для WR с таким низким
базовым рейтом).
