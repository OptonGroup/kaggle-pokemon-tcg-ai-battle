# Latest Matchup WR — быстрый чек живого WR по архетипам

Лёгкая версия `replay-analyzer`: НЕ разбирает причины поражений по ходам, только
скачивает реплеи и считает W/L по каждому архетипу соперника у двух последних сабмитов.
Если это identical double-submit (два байт-идентичных копии одной версии, тактика из
`reference_forum_727695_leaderboard_slot_machine`) — считать СУММАРНО как одну версию.
Если это две разные версии — считать РАЗДЕЛЬНО (не смешивать).

## Шаг 1 — Найти два последних сабмита и понять: идентичны или разные

```bash
.venv/bin/kaggle competitions submissions -c pokemon-tcg-ai-battle | head -5
```

Взять два самых свежих по дате (верхние строки). Определить идентичность по:
- `fileName` — если одинаковый tar.gz для обеих строк, и/или
- `description` — явно говорит "identical", "copy A"/"copy B", "byte-identical" (проект
  использует эту тактику намеренно, см. `results/submissions.csv` — записи вида
  `vNNN_xxx` с двумя ref в одной строке "IDENTICAL DOUBLE-SUBMIT: refs A + B").

Если сабмиты РАЗНЫЕ версии (разные main.py/деки) — не считать их одним пулом.

## Шаг 2 — Скачать реплеи обеих копий

```bash
.venv/bin/python scripts/download_episodes.py out/<version>_wr_check A=<ref1> B=<ref2>
```

Идемпотентно (существующие файлы не перекачиваются) — можно передопускать, если юзер
спрашивает повторно позже в тот же день для свежих игр.

## Шаг 3 — Классифицировать архетип соперника и посчитать WR

```bash
.venv/bin/python scripts/classify_opponent_archetype.py out/<version>_wr_check
```

Печатает: общий WR по лестнице, COMBINED-таблицу WR по архетипу (обе копии вместе) и
ОТДЕЛЬНУЮ таблицу на каждый `submission_id` (копия A / копия B) — то есть обе разбивки
доступны сразу, выбор "суммировать или разделить" из Шага 1 просто определяет, какую
таблицу показывать юзеру как главную.

Архетип определяется по РЕАЛЬНОМУ составу колоды соперника (initial deck из реплея),
а не по нашему `detect_matchup()` во время игры — тот основан на неполном борде и может
ошибаться. Список известных архетипов и их key-card id — в `ARCHETYPE_IDS`/`NAME_KEYWORDS`
внутри скрипта.

Self-validation игры (`opp_team_name` пусто) автоматически исключены из WR-счёта.

## Шаг 4 — Отчёт юзеру

Кратко, по-русски:
- Текущий live-score каждой копии (из вывода Шага 1) + сколько ладдер-игр сыграно.
- Итоговый WR (суммарно, если идентичны; раздельно, если разные версии).
- Таблица WR по архетипу, отсортированная по числу игр.
- Оговорка про размер выборки: см. `reference_sample_size_for_live_eval` — matchup-статистика
  надёжна только при ~150 играх на архетип, при малом N (<10 на архетип) явно предупредить,
  что это шум, а не вывод.

НЕ запускать глубокий per-episode misplay-разбор (это `replay-analyzer`) и НЕ сабмитить
ничего на Kaggle — это чисто read-only отчёт.

## Грабли

- **Общие тех-карты ложно матчат архетип по id.** Пример: card id 140 (Fezandipiti ex) —
  частый support, НЕ эксклюзивен для Alakazam; изначально попал в `ARCHETYPE_IDS["alakazam"]`
  и ложно классифицировал Dragapult-колоды (Drakloak/Dreepy без единой Alakazam-карты) как
  alakazam. Правило: в `ARCHETYPE_IDS` класть ТОЛЬКО card id самой эволюционной линии
  архетипа (базовая+эволюции+ex), никогда generic support/item/stadium, даже если он часто
  встречается в этом архетипе.
- Новый архетип без совпадения по `ARCHETYPE_IDS`/`NAME_KEYWORDS` попадёт в `UNKNOWN` —
  посмотреть `opp_key_cards` в выводе/`archetype_index.csv` и добавить в один из двух
  словарей в `scripts/classify_opponent_archetype.py`.
- Рейт-лимит Kaggle API — скрипт скачивания уже держит ≤2 потока с 429-бэкоффом
  (см. `project_kaggle_kgat_token`), не увеличивать concurrency.
- Один реплей ~3.3МБ — скрипт классификации сам находит initial deck внутри JSON
  (`find_initial_players`), читать сырой реплей руками не нужно.
