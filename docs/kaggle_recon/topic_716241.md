### TL;DR

In one recorded `cabt` replay, a player plays **Rare Candy** to skip-evolve a Basic Pokémon
into a Stage 2 Pokémon. The engine:

1. offers the evolution as a legal option,
2. the player selects it,
3. consumes the Rare Candy,

but then the engine does **not** perform the evolution.

Across **660** Rare Candy skip-evolution events in a 5,200-game replay corpus, this happened
**exactly once**. Every other event, including cases with the same deck, the same card, and the
same observable signature, evolved correctly.

From the observation-level data available, no observable game-state feature distinguishes this
non-evolving case from correctly-evolving cases. Appears more consistent with a rare
internal-state-dependent engine issue than a normal rules edge case, but root cause cannot be
confirmed without engine source or state injection.

- **Card:** `1079` ふしぎなアメ / **Rare Candy**
- **Expected behavior:** the selected Basic Pokémon should evolve into the chosen Stage 2 Pokémon.
- **Observed behavior:** Rare Candy is consumed, but the Pokémon is **not** evolved.

- Engine: **cabt** simulator (`libcg.so`), driven via `kaggle-environments`.
- Replays are **cabt self-play games** recorded in the standard `kaggle-environments` step format.
  - Each step is a list of per-player views with `action`, `observation`, and `status`.
  - `observation.logs` is the engine event log.

### Reproduction: the divergent decision

Bug replay: `meta_cl_c55__vs__cl_c550__g1`, player 1, turn 18, step 86.

At this point:
- Player 1's board:
  - Active: Axew `548`, serial `71`, HP `100/100`, 1 energy attached
  - Bench: Axew `548`, serial `68`
- Player 1's hand:
  - 3× Haxorus `550`, serials `64`, `63`, `65`
  - 1× Fraxure `549`, serial `66`
  - energies
  - 1 other card

Player 1 plays **Rare Candy `1079`** with serial `73`. Engine presents a `select` prompt with
`context: 37` (Rare Candy skip-evolution choice). The prompt contains **6 options**:

```
{3 Haxorus in hand} × {Active Axew, Bench Axew}
```

Player 1's action is `[0]`, which selects:

```json
{"type":9,"area":2,"index":0,"inPlayArea":4,"inPlayIndex":0}
```

Interpreted as:
- `type 9` = evolve
- `area 2, index 0` = Haxorus from hand, serial `64`
- `inPlayArea 4, inPlayIndex 0` = Active Pokémon, Axew serial `71`

So the selected action is: evolve hand Haxorus `550` (serial 64) onto Active Axew `548` (serial 71).

The engine logs the Rare Candy use, but **no evolution event** is emitted. The Active Pokémon
remains Axew `548` with serial `71`; later steps show it continuing to attack as Axew. Its HP

### Why this looks like a possible bug

The engine itself offered the evolution as a legal option (`select.context = 37`,
`option type = 9`) and the player selected it. Given that, the engine seems internally
inconsistent in this replay:
- either the evolution should not have been offered,
- or, once selected, the evolution should have been performed.

Consuming Rare Candy while silently skipping the selected evolution does not seem consistent
with either behavior. The target appears valid from the observable state: it is a Basic
Pokémon, it has a matching Stage 2 Pokémon in hand, `appearThisTurn: false`, and the engine
offered the evolution option. In the replay corpus, **659 of 660** Rare Candy events evolved
correctly, including events involving this same card and the same deck.

### Frequency analysis

Scanned all **660** `context 37` Rare Candy events in a 5,200-game replay corpus. Only **1**
event did not evolve: the case described above. Tried to find any observable feature that
separates this case from the 659 correct cases — every candidate feature was refuted by at
least one correctly-evolving counterexample with the same value.

| candidate feature | bug-case value | result |
|---|---|---|
| same cardId, Axew `548` | `548` | refuted; Axew evolves elsewhere (e.g. `cl_c994 g2`) |
| duplicate of the Basic on board | yes, Bench also has Axew | refuted; 400 evolving events also have a duplicate Basic on board, including same-deck games `cl_c55 g0/g3` |
| target is Active vs Bench | Active | refuted |
| Stage 1 Fraxure `549` in hand | yes | refuted; 202 evolving events also have the Stage 1 in hand (`cl_c994 g2`) |
| target promoted this turn | no | refuted |
| number of options offered | 6 | refuted; 30 evolving events also have 6 options |
| number of Stage 2 cards in hand | 3 | refuted; 15 evolving events also have 3 Stage 2 cards in hand |

From the observation-level features extractable, this non-evolving case shares its observable
signature with multiple correctly-evolving games. No observable game-state feature
distinguishes it.

### Why ordinary per-event randomness seems unlikely

Rare Candy resolution is not a coin-flip or shuffle mechanic. If caused by an ordinary
randomized branch, more than a single isolated case across 660 events would be expected
(unless the branch probability is extremely small). Each replay is a deterministic recorded
`kaggle-environments` replay. Observed pattern: 1/660 cases, same observable signature as
correct cases, not explained by any tested observable feature. Looks more like a rare
internal-state-dependent engine behavior than a normal rules edge case. Without engine
source or the ability to inject exact internal state, root cause cannot be determined.

### Suggested way to confirm

Requires engine source access or the ability to re-run from an exact internal state. Useful
confirmation: re-run the engine from the exact internal state at step 86 of the bug replay
multiple times.
- If it always fails to evolve → suggests a deterministic bug in the Rare Candy resolution
  path for that internal state.
- If the result varies → suggests non-determinism, such as uninitialized state or
  ordering-dependent behavior.

Only observation-level replays available, so this test cannot be performed by the poster.

## POST 2 (reply) — author: 실험용생쥐 — 2026-07-03 19:19:45 UTC — votes: 0

Thanks for the detailed post! I tried to reproduce it, and I think the trigger is **Bronzong's
Evolution Jammer**.

In the failed case, the turn before, the Active was hit by Evolution Jammer. So on that turn
the player cannot evolve from hand. But the two evolve paths behave differently:

- **normal evolve menu:** it correctly hides the evolve option when you are jammed.
- **Rare Candy:** it still shows the evolve option even when you are jammed. If you pick it, the
  Rare Candy is discarded but no evolution happens.

This matches the original findings. It is rare because Evolution Jammer is not a common card,
and the effect only lasts 1 turn. And no board/hand feature can tell it apart, because the
"cannot evolve this turn" state is **not in the observation**.

Test method: let the opponent hit my Active with Evolution Jammer, then next turn use Rare
Candy to evolve a Basic into its Stage 2.

- **with jammer:** 100+ plays, every time the Rare Candy is used but no evolve (the Pokemon stays
  Basic, the candy goes to discard).
- **without jammer (control):** the same play evolves every time (hundreds of plays, 0 fail).

Suggested fix: when the player is under Evolution Jammer, the Rare Candy evolve should also be
blocked (or the candy should not be consumed), same as the normal evolve menu already does.
