### Notebook description (markdown cell)

Title: "Master Telemetry & Metrics Curation Matrix"
Built for the Pokémon TCG AI Battle Challenge.

This notebook provides a robust, null-safe parsing engine to extract structured
match telemetry from raw JSON hopper logs.

Features:
- Dynamic Team Tracking: Automatically identifies your target team index (0 or 1).
- Structural Fallbacks: Handles shifting schema formats (`observation` vs. `obs`) across different match steps.
- Targeted Metrics: Tracks maximum grid energy, specific attack executions, and bench lock turns.

How to Use:
1. Ensure your raw JSON logs are loaded into the Kaggle input directory.
2. Update the `USER VARIABLES` in the first code cell with your specific team name and target card ID.
3. Run all cells. The notebook will output a `curated_telemetry.csv` file to your working directory.

### Parsing logic (key code)

The notebook's `run_master_telemetry()` function iterates over replay JSON files
and extracts per-match metrics:

1. **Dynamic team tracking:** Reads `data["info"]["TeamNames"]`, finds the index
   of `TARGET_TEAM_NAME`. Falls back to index 1 if name not found.

2. **Schema fallback for observation:** For each step, tries three keys in order:
   `step[0]["current"]` → `step[0]["observation"]["current"]` →
   `step[0]["obs"]["current"]`. This handles shifting schema formats across
   different match steps.

3. **Max Grid Energy:** Sums `len(p["energies"])` across active + bench Pokémon
   for the target player at each step; tracks the maximum across the match.

4. **Target Attack Executions:** Reads step logs (with same `observation`/`obs`
   fallback), counts log entries where `log["playerIndex"] == target_index` AND
   `log["cardId"] == target_card_id` AND `log["type"]` is "15" or "attack".

5. **Bench Lock Turns:** Counts steps where the target player's bench has >= 5
   Pokémon (bench full / locked).

6. **Output:** Writes `curated_telemetry.csv` with columns:
   Match_ID, Max_Grid_Energy, Target_Attack_Executions, Bench_Lock_Turns.

### Notable technical observations from the code

- The replay JSON structure has an `info.TeamNames` array for team identification.
- Steps are arrays where `step[0]` contains the observation dict.
- The observation schema is NOT consistent across steps — some use `current`,
  some `observation.current`, some `obs.current`. This confirms the replay format
  has shifting schema formats that require fallback parsing.
- Log entries have `playerIndex`, `cardId`, and `type` fields. Attack type is
  represented as either string "15" or string "attack" (type code 15 = attack).
- `energies` is a list on each Pokémon object.
- `bench` and `active` are lists on each player object.
- `players` is a list indexed by team (0 or 1).
