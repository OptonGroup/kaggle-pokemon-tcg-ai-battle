## Методология и ограничения

- **Окно данных: 2026-07-29 — 2026-07-31.** 08-01 недоступен на Kaggle на момент сбора,
  добавить позже отдельным шагом.
- **КАВЕАТ про рейтинг — самое важное ограничение всего отчёта.** Датасет реплеев не
  содержит рейтинг команды на момент конкретной игры. `rating_a`/`rating_b` получены
  джойном team-name → ТЕКУЩИЙ (на 2026-07-30) локальный снэпшот паблик-лидерборда
  (`out/scout_evo_wr_check/pokemon-tcg-ai-battle-publicleaderboard-2026-07-30T19:22:47.csv`,
  самый свежий по mtime среди `out/`, `docs/gold/`, `scratchpad/gold/`). Это НЕ
  point-in-time рейтинг: если команда сильно двигалась по лидерборду за окно, её
  рейтинг на момент конкретной игры мог отличаться от снэпшота. У ~3.5% сторон
  (929 из 26192) рейтинг пустой — команда не нашлась в снэпшоте; такие строки просто
  исключены из всех расчётов, требующих рейтинг (бэнды, MH-страты), без попыток угадать
  значение. Это ограничение принято и не блокирует расчёт — это лучшее доступное
  приближение и именно то, что предполагалось использовать (сила пилота коррелирует с
  текущим рейтингом даже при лаге в несколько дней).
- **N<150 — не доверять.** По методике с форума (медианное смещение WR 20.8 пп при
  N<150 vs 1.9 пп при N≥4000) все ячейки матчап-матрицы (б) с N<150 помечены `*`
  явно и не должны использоваться как решающий сигнал в одиночку.
- **MH-скорректированный WR — приближение.** `mantel_haenszel()` возвращает
  Cochran–Mantel–Haenszel odds ratio (OR_MH) и p-value, не WR напрямую. Чтобы получить
  число, сравнимое с сырым WR (как у Sumi: 54.2% → 50.6%), используется стандартное
  приближение `WR_MH ≈ OR_MH / (1 + OR_MH)`, то есть odds ratio конвертируется в
  вероятность в предположении, что средний WR поля-сравнения (не-кандидат, тот же
  бенд разницы рейтингов) близок к 50%. Это разумное приближение при малой доле
  кандидата в общем пуле (что верно для всех 4 кандидатов здесь: 376–707 из 26192
  сторон), но не точная величина — в тексте раздела (в) дельта считается как
  `WR_MH − 50%`, а не как прямое сравнение с сырым WR поля.
- **Страты MH = бины по 50 очков от `rating_a − rating_b`** (для стороны-кандидата:
  собственный рейтинг минус рейтинг оппонента), а не абсолютный бенд оппонента (как
  в `CROSS_VERSION_LEDGER.md`) — это прямее контролирует именно разницу силы в
  конкретной игре, как и просил план. Игры без рейтинга хотя бы одной стороны
  исключены из MH (но не из сырого WR — см. таблицу (в), колонки N различаются).
- Данные — только 3 источника окна (без реплеев наших версий), это ladder-игры между
  произвольными паблик-командами, не наши собственные сабмиты.

raw-порога паритета). Для `lopunny` рост означает, что в среднем эта сторона играла
против оппонентов с БОЛЕЕ высоким рейтингом, чем предполагает сырой WR (т.е. сырые
62.5% недооценивают истинный edge относительно того, что обычно бывает эффект
инфляции WR слабыми оппонентами — здесь наоборот).

## Критерий выбора деки (напоминание, решение — не в рамках этого шага)

Кандидат берётся в работу, если после MH-поправки его WR против поля **≥ +5 пп при
p<0.01 и N≥100** за окно. При N<100 — не отбрасывать, отметить «нужно докачать ещё
день данных». Выбор конкретной деки для следующего сабмита — отдельный шаг, здесь
только даны цифры.

## Приложение: как считалось

Эфемерные скрипты анализа (не сохранены в репозитории по запросу — использовался
временный scratch-каталог сессии):
1. Построение long-формата «сторон» (`team_a`/`team_b` → 2 строки на игру) из
   `games.csv`.
2. (а) — группировка по бэнду рейтинга (100 очков, `1000-1099`/`1100+` отдельно),
   доля каждого архетипа внутри бэнда.
3. (б) — группировка по `(own_arche, opp_arche)`, `wilson_ci()` на каждую ячейку.
4. (в) — для каждого кандидата: raw WR = среднее по всем некейс-зеркальным сторонам
   кандидата; для MH — `rows` = все стороны с известным рейтингом обеих сторон
   (искл. зеркало кандидата), `band = floor((rating_own − rating_opp)/50)*50`,
   вызов `mantel_haenszel(rows, target=архетип)` из
   `scripts/cross_version_matchup_ledger.py` без изменений сигнатуры/логики.
5. (г) — джойн по `TeamName` из самого свежего `*leaderboard*.csv` (по mtime),
   топ-20 по `Score`, подсчёт архетипов по имени команды в `games.csv`.
