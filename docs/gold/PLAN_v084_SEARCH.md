## 1. Почему search-override, а не что-то ещё

- Бюджет: v083 тратит **0.8-1.5 мс/решение при доступных 3.6-10 с/решение**
  (банк 600 с/эпизод, 60-165 решений/партию) — единственный ресурс задачи,
  задействованный на <0.1%.
- Existence proof НА НАШЕМ ДВИЖКЕ И ЛАДДЕРЕ: jazivxt (Magist, **994.2**) — эвристика
  + 2-ply determinized search как override; та же схема переиспользована
  prvsiyan_v9 и (упрощённо) nursrijan_lucario (заявл. 1091). 3 из топовых агентов
  поля гоняют `search_begin/search_step` в проде.
- Наш прецедент «KILL_PIMC» (07-12) **не про эту конструкцию**: там rollout обеих
  сторон до терминала своей политикой без leaf-оценки. Оговорка в
  `RESTART_BRIEF_2026-08-01.md:292-293,344`: с обученной/внешней оценкой листа вывод
  не переносится (подтверждено scout +5.8пп p=0.0002 — единственный измеренный
  проход порога в истории проекта).
- Margin-override ограничивает даунсайд: поиск **переопределяет BC только при
  перевесе ≥ пол-приза** в шкале leaf-eval; худший случай ≈ v083 минус редкие
  ошибочные оверрайды.

### 2.1 Схема решения (порт СХЕМЫ jazivxt, реализация своя — §6.3 запрещает чужой код)

1. **Гейт входа**: context==MAIN, 3 ≤ n_options ≤ 24, turn ≥ 2, BC отработал
   (`_bc_decide` вернул скоры), эпизодный банк не исчерпан.
2. **Кандидаты**: top-K по скорам BC (K=6, включая BC-top-1 = incumbent).
   Не по типам опций (`_smart_candidates` из мёртвой PIMC-линии не брать).
3. **Детерминизация** (N_DET=3): своя колода/призы = 60-лист минус видимое;
   оппонент = шаблон архетипа через уже провалидированный `_detect_matchup_raw`
   (254/254, детект к ходу 2) + деки-шаблоны; фолбэк без матча — синтетика
   (самая частая видимая карта ×30 + базовая энергия доминирующего типа ×30 +
   dummy basic) — схема jazivxt `_sample_hidden`.
4. **Дерево (2-ply)**: `search_begin(obs, **hidden)` на детерминизацию → на каждого
   кандидата `search_step` → жадное доигрывание СВОЕГО хода до передачи хода
   (cap шагов) → резолв форс-выборов → на MAIN оппонента: top-K_OPP=3 его опций по
   упорядочивающей функции, каждая ветка жадно доигрывается до конца его хода →
   **min** по веткам → leaf-eval. `search_end()` в `finally` на каждое решение
   (пул состояний движка = 128, утечка 150МБ без освобождения; `search_release`
   промежуточных состояний по мере продвижения).
5. **Leaf-eval v1** (линейная, своя): 1000·(призы_опп − наши) + Σhp_наши − Σhp_опп +
   5·Δэнергий − 4000·(нет актива); терминал ±1e7. (v2 — обученная GBM-value по
   схеме scout `train_value2.py` — отдельная итерация, только если v1 прошла гейт.)
6. **Упорядочивание ходов оппонента**: зеркало → BC (оппонент играет наш лист —
   легитимно); не-зеркало → генерик-скорер (ATTACK по урону > ABILITY > ATTACH/PLAY
   > RETREAT > END), своя реализация.
7. **Решение**: среднее leaf по детерминизациям, честное сравнение только кандидатов
   с равным числом оценок (правило n_top jazivxt). **Override BC-top-1 только если
   avg(best) ≥ avg(incumbent) + 500** (пол-приза).

### 2.2 Бюджет и деградация (порт паттерна scout_deeper)

- TIME_BUDGET_S = 0.8/решение, единый deadline, проверяемый на каждом уровне циклов.
- Эпизодный банк: `_SPENT` сбрасывается при `sel is None`; SOFT = 380 с → N_DET=1;
  HARD = 520 с → поиск off до конца партии. (Порог перекалибровать по смоуку —
  тайминги scout не переносятся.)
- **Never-throw**: весь поиск в try/except → возврат BC-pick; ≥3 исключений за
  партию → поиск off до конца партии; никакой путь не может вернуть невалидный
  индекс (кандидаты — только реальные индексы опций корня).
- **Per-decision stderr-трейс обязателен**: `src=search|bc`, ms, spent, ndet,
  n_cands, margin, override y/n — расширение существующего `_dbg`.

archaludon −13.2пп на ОБОИХ независимых оппонентах (z≈−4.8), mirror −11.5пп (z=−4.05),
lucario −4.5, alakazam −3.8, crustle_mill +0.8 (контрольная ≈0 — прибор исправен).

Механизм (майнинг 432k трейс-решений `out/gate_pool2/v084s_run.log`): 12 582 оверрайда
(2.9% решений), медианный margin ≈1 приз, верхние ~12% — «терминальные» находки ±1e7
(поиск «видит» форс-выигрыш в мире, где оппонент = генерик-скорер, и ошибается).
Margin-порог не спасает: смещена сама оценка, а не её дисперсия.

**Вывод**: схема jazivxt дословно (линейный лист + генерик-rollout) на НАШЕМ стеке
опровергнута — BC-политика сильнее rollout-политики, поиск деградирует её (пятое
подтверждение «ручная оценка не проходит гейт»). Это сходится с предупреждением
recon: единственный работавший дизайн — scout (обученный лист + своя политика в
rollout). Разница с jazivxt: его rollout-политика = его полная прод-эвристика,
а наша v1 — таблица приоритетов типов.
